# สรุป bake-off และข้อเสนอ production: ทำไมต้องเป็น GLiNER-Relex

> เอกสารนี้เขียนสำหรับคนที่ไม่ได้อยู่ใน domain NLP/information extraction
> อ่านจบแล้วควรเข้าใจได้ว่า ทำไมเราเลือก GLiNER-Relex ไปรันใน production
> และตัวเลขอย่าง "~0.88 @ th 0.9" แปลว่าอะไร

---

## 1. บริบท: เรากำลังแก้ปัญหาอะไร

เป้าหมายของโปรเจกต์คือสร้าง **extractor ที่อ่านงานวิจัย (paper) แล้วดึงความสัมพันธ์
ออกมาเป็น (subject, relation, object)** เพื่อป้อนเข้า knowledge graph
ตัวอย่างจาก paper domain:

```
("BERT", "pretrained on", "BooksCorpus")
("T5", "evaluated on", "SuperGLUE")
("DistilBERT", "outperforms", "BERT-base")
```

สิ่งที่ต้องการเรียกว่า **triple extraction** — แต่ละ triple คือหนึ่งเส้นเชื่อม
ในกราฟความรู้ (node = entity, edge = relation)

### Bake-off คืออะไร

เราไม่เดาว่าโมเดลไหนดี เราจัดการแข่งขัน (bake-off) โดยปล่อย **ชุดทดสอบ 28
ประโยคจริงจาก paper** (แบ่งเป็น 7 category: alias, comparison, training,
benchmark, effect, multi-rel, hard) ให้โมเดล 5 ตัวชิงกัน:

| โมเดล | ประเภท |
|---|---|
| gliner-relex | encoder zero-shot สำหรับ IE โดยเฉพาะ |
| glirel | encoder zero-shot relation extraction |
| gliner-pyrheads | encoder zero-shot อีกสถาปัตยกรรม |
| relik | pipeline แบบ schema ปิด (อธิบายใน §4) |
| nuextract | LLM ตัวเล็ก (2B) ที่ fine-tune มาเพื่อ extract ข้อมูลตาม schema |

ทุกตัวให้ schema เดียวกัน (ชุด relation เป้าหมาย เช่น `pretrained on`,
`outperforms`) ยกเว้น relik ที่ปิด schema ไม่รับ

## 2. อ่านตัวเลขให้เป็น: precision, threshold, และเครื่องหมาย ~

### 2.1 Precision คืออะไร

**Precision = จาก triple ที่โมเดลตอบออกมาทั้งหมด มีกี่เปอร์เซ็นต์ที่ถูกต้องจริง**

- precision 0.88 = โมเดลตอบมา 100 อัน ผิด ~12 อัน
- อย่าสับสนกับ **recall** = จากความสัมพันธ์ที่*มีอยู่จริง*ใน text จับได้กี่เปอร์เซ็นต์
  (bake-off นี้**ไม่ได้วัด recall** เพราะไม่มี ground truth ครบทุกประโยค —
  เราเก็บข้อจำกัดนี้ไว้ใน §7)

สำหรับ use case ของเรา precision สำคัญกว่า: **triple ผิดที่หลุดเข้ากราฟไปแล้ว
ต้องมานั่งลบทีหลัง** แพงกว่าความสัมพันธ์ที่พลาดไปหลายเท่า
(อ่านต่อ §6 ว่าเราไม่ได้ปล่อย recall ทิ้ง)

### 2.2 Threshold คืออะไร แล้ว "~0.88 @ th 0.9" แปลว่าอะไร

โมเดลพวกนี้ไม่ได้ตอบแค่ "ใช่/ไม่ใช่" — มันให้ **score (ความมั่นใจ) กับทุก
candidate triple** เช่น 0.97, 0.72, 0.51

จากนั้นเราเลือกเส้นตัด (threshold) ว่า score ต่ำกว่าเท่าไหร่ถึงจะทิ้ง:

> **~0.88 @ th 0.9** = "ถ้าเชื่อเฉพาะ triple ที่ score ≥ 0.9
> precision จะอยู่ราว ๆ 88%"

ผลคือเกิด **trade-off ตามธรรมชาติ**:

| threshold | ได้ triple | precision | ความหมาย |
|---|---|---|---|
| ต่ำ (0.3) | เยอะ | ต่ำ | จับได้เกือบหมด แต่ขยะเยอะ |
| สูง (0.9) | น้อย | สูง | เชื่อได้แทบทุกอัน แต่พลาดบ้างที่จริง |

ดูข้อมูลจริงของ gliner-relex:

| th | #triples | precision ~ | ประโยคว่าง |
|---|---|---|---|
| 0.3 | 233 | ~0.39 | 0 |
| 0.5 | 139 | ~0.52 | 0 |
| 0.7 | 92 | ~0.66 | 1 |
| **0.9** | **33** | **~0.88** | 9 |

ยิ่งตัดสูง ยิ่งเหลือน้อย — ถึง th 0.9 มี 9/28 ประโยคที่ไม่เหลือ triple เลย

**จุดแข็งของ encoder models: threshold แก้ได้ฟรีหลังรันเสร็จ**
เพราะเราเก็บ raw scores ไว้ ตัดที่ 0.5, 0.7, 0.9 ก็แค่ slice ข้อมูลเดิม
ไม่ต้องรันโมเดลใหม่ (นี่คือเหตุผลที่ report แสดง 4 thresholds ต่อโมเดล)

### 2.3 ทำไมมีเครื่องหมาย ~ (tilde)

เพราะ precision ค่านี้ **ประเมินด้วยคน (eyeball rating) ไม่ใช่ script**
— เราเก็บ triple unique ทั้งหมดมาให้คนตัดสิน "triple นี้ถูกต้องตามที่ประโยคพูดไหม"
ครั้งเดียวต่อ triple แล้วคำนวณ precision ของทุก threshold จากคะแนนชุดเดียวกัน

~0.88 จึงแปลว่า "ราว 88% ตามการตัดสินของคน 1 คน บนชุดขนาด 33 triples"
ไม่ใช่ค่าที่ reproduce แบบ statistical ได้แม่นเป๊ะ — แต่เพียงพอสำหรับการ
**จัดอันดับเทียบกัน** เพราะทุกโมเดลโดนประเมินด้วยวิธีเดียวกัน

### 2.4 "ประโยคว่าง" คือสัญญาณของ recall ที่ยังไม่เห็น

คอลัมน์ "ประโยคว่าง" = ประโยคที่หลังตัด threshold แล้วไม่เหลือ triple สักอัน
ถ้าประโยคนั้นมีความสัมพันธ์อยู่จริง แปลว่าโมเดลพลาดมันไป — **นี่คือ recall
ที่รั่วไหลแต่วัดไม่ได้ตรง ๆ** จึงใช้เป็นสัญญาณแทน

ตัวอย่างชัด ๆ คือ nuextract: ที่ th 0.98 มันเหลือ 2 triples จาก 28 ประโยค
(ว่าง 26/28) — ส่วนใหญ่ของที่มันเคยตอบมาโดนทิ้งหมด

## 3. อันดับความแม่ยำ (มาก → น้อย)

1. **gliner-relex — ~0.88 @ th 0.9**
   ตัวเดียวที่ได้ precision สูง *พร้อม* เหลือผลลัพธ์จำนวนมากพอจะใช้งานได้จริง
   (33 triples) และถ้าผ่อน threshold ลงก็ยังมี curve ที่ลื่น: 0.66 @ th 0.7,
   0.52 @ th 0.5 — ปรับจุดตัดตามความต้องการได้

2. **nuextract — ~1.00 @ th 0.98** *(มีเงื่อนไขใหญ่ ดู §4)*
   ตัวเลขสวยที่สุดบนกระดาษ แต่มาจากฐาน 2 triples เท่านั้น — precision 100%
   ของ 2 อัน สู้ 88% ของ 33 อันไม่ได้ในทางสถิติ และแปลว่าโมเดลเกือบจะ
   "ไม่กล้าตอบ" อะไรเลย

3. **gliner-pyrheads — ~0.53 @ th 0.85**
   กึ่งกลาง เหลือ 73 triples แต่กว่าครึ่งเป็นขยะ สำหรับกราฟที่ต้องการคุณภาพ
   ถือว่าต่ำเกิน

4. **glirel — ~0.14 @ th 0.25**
   แม่แค่ 14% — ตอบเยอะแต่ขยะเยอะ และ score distribution ของมันแย่มาก
   (ผ่อน threshold ลงก็ไม่ช่วย: ทุก threshold precision แย่เท่ากัน)

5. **relik — ~0.00**
   แทบไม่มีอะไรถูกเลย แต่ต้องอ่านเป็นธรรมกับมันก่อน (§4)

## 4. กับดักที่ต้องเข้าใจก่อนอ่านตาราง

### nuextract: precision 1.00 ที่หลอกตา

ถ้าดูแค่ชื่อคอลัมน์ "precision ~ (best th)" nuextract เป็นเบอร์หนึ่ง
แต่ดูแถว th 0.98 ของมัน: **42 triples ที่ตอบมา โดนตัดเหลือ 2 ประโยคว่าง 26/28**

นี่คือรูปแบบคลาสสิกของโมเดลที่ score distribution สูงผิดปกติ (LLM ให้ token
probability สูงมากกับทุกอย่างที่มันเขียนออกมา) — พอเรายก threshold ไป 0.98
มันไม่ได้ "เหลือเฉพาะที่ถูก" แต่ "ทิ้งแทบทุกอย่าง" และ 2 อันที่เหลือบังเอิญถูก

ที่ threshold ที่ใช้งานได้จริงของมัน (0.85–0.9) precision คือ ~0.55–0.56 —
แพ้ gliner-relex ชัดเจน สรุป: **nuextract ไม่ได้แม่กว่า มันแค่เงียบเก่ง**

### relik: 0.00 ไม่ใช่ความผิดของมันทั้งหมด

relik เป็นโมเดล **schema ปิด** — reader ของมันถูกฝึกบน dataset NYT (ข่าว:
สถานที่เกิด, ตำแหน่ง, ทีมกีฬา ฯลฯ) ไม่รับ relation ที่เราสนใจ (`pretrained on`,
`outperforms` ฯลฯ) เราจึงรันด้วย native schema ตามความจริงที่ว่ามันใช้กับงาน
paper ไม่ได้อยู่แล้ว

ผลที่ได้ (relations แบบ `place of birth`, `sports team` โผล่มา 24 อัน)
ยืนยันสิ่งที่รู้อยู่แล้ว: **มันถูก disqualify ด้วยเหตุ schema ไม่ใช่เพราะ
โมเดลไม่ดี** — แต่สำหรับ use case นี้ สรุปเดิม: ใช้ไม่ได้

### schema เปิด vs ปิด ทำไมสำคัญ

- **schema ปิด** (relik): ทำนายได้เฉพาะ relation ที่เคยเห็นตอน train
  เร็ว แข็งแรง แต่ locked กับ domain ของ training data
- **schema เปิด** (gliner-relex, glirel, gliner-pyrheads, nuextract):
  เรา "บอก" ชุด relation ที่ต้องการตอน inference (seed relations)
  จึงปรับ domain ได้โดยไม่ต้อง train ใหม่ — ตรงกับความต้องการเราเป๊ะ

ข้อสังเกตจาก distinct relations: gliner-relex ผลิต relation ตรง seed ทั้ง 10 อัน
สะอาด ไม่หลุดไปคำอื่น เทียบกับ nuextract ที่ตอบมา 17 อันรวม variant มั่ว ๆ
อย่าง `achieves` vs `achieves metric`, `improves` vs `improves upon` —
normalization ต้องตามเก็บเพิ่ม

## 5. ตัดสินใจ: gliner-relex สำหรับ production

Workload ที่ต้องรองรับ:

- ไม่ realtime — เป็น batch job (1–10 papers ต่อรอบ)
- ~100 papers/day
- deploy บน GPU

### 5.1 ความแม่: ชนะชัด ๆ ในกลุ่มที่ใช้ได้

เหลือเพียง 4 ตัว schema เปิดให้เทียบจริง แล้ว gliner-relex ชนะทั้ง precision
(0.88 เทียบ 0.53 / 0.14 / 0.55) และความสะอาดของ relation output

### 5.2 ความเร็ว: เกินพอสำหรับ workload นี้หลายเท่า

**15.5 ms/ประโยค** (หลัง warm-up, บน GPU)

ประมาณการหยาบ ๆ: paper หนึ่งฉบับ ~300 ประโยคที่เข้าข่าย →
100 papers × 300 ประโยค × 15.5 ms ≈ **7.75 นาที/วัน** สำหรับทั้งวัน
แม้ประมาณการผิด 5–10 เท่าก็ยังเป็นงานไม่กี่สิบนาที — เทียบกับ nuextract
(976.6 ms/ประโยค ≈ 8 ชม./วัน ที่ปริมาณเดียวกัน) ที่จะกลายเป็น bottleneck
ทั้งระบบ

เนื่องจากไม่ realtime + batch เล็ก แม้แต่ตัวที่ช้ากว่าก็ "พอไหว" ทางทฤษฎี
แต่ไม่มีเหตุผลจ่ายค่า latency 50–60× เพื่อได้ผลแย่กว่า

### 5.3 ทรัพยากร: เบาที่สุดในกลุ่ม

**VRAM peak 1.29 GiB** — น้อยที่สุดใน 5 ตัว (nuextract 4.39 GiB, glirel 3.32 GiB)
แปลว่า:

- GPU รุ่นไหนก็รันได้ แม้แต่การ์ดเก่า/ขนาดเล็ก
- co-locate กับ service อื่นบน GPU เดียวกันได้สบาย
- ต้นทุน infra ต่ำที่สุดในทางเลือกทั้งหมด

### 5.4 ตัดสินใจ threshold ตอน deploy

จาก sweep เราขอเสนอ **เริ่มที่ th 0.9 (precision ~0.88)** เพราะเชื่อแนวคิด
"triple ผิดแพงกว่า triple ที่พลาด" (§2.1) แล้วเก็บ raw scores ไว้เสมอ
เพื่อผ่อนลงได้ทีหลังโดยไม่ต้อง rerun:

- ถ้าเจอว่ากราฟโหว่เกิน (recall ต่ำเกิน) → ผ่อนเป็น 0.7 (0.66) หรือ 0.5 (0.52)
- มี option ระดับกลาง 0.65 ตามที่วางไว้ตั้งแต่ design phase

นี่คือ benefit เชิงระบบที่ bake-off ออกแบบให้ตั้งแต่ต้น:
**rate once, slice many** — ตัดสินใจ threshold ได้ภายหลัง แม้หลังข้อมูลเข้าระบบแล้ว

## 6. แผนรับมือ recall (สิ่งที่ bake-off วัดไม่ได้)

Precision สูง ≠ จับได้ครบ และเรายังไม่มี ground truth เต็ม จึงวางแนวทางไว้:

1. **threshold ต่ำไว้ก่อนใน tier แรก** — เก็บ triple ที่ 0.5–0.9 ไว้ในสถานะ
   "รอ review" แทนการทิ้ง precision ยังคุมด้วย UI ฝั่ง human-in-the-loop
2. **รวม triple ของหลาย threshold เป็น candidate pool** — เพราะเราเก็บ raw
   scores ต้นทุนเพิ่มเป็นศูนย์
3. **เก็บ precision ต่อเนื่อง** — sample triple จาก production มาตรวจด้วยตา
   เป็นระยะ เพื่อยืนยันว่าคุณภาพไม่ตกจากที่ bake-off เห็น (distribution ของ
   paper จริงอาจต่างจาก 28 ประโยคทดสอบ)

## 7. ข้อจำกัดของ bake-off นี้ (อ่านก่อนอ้างอิงตัวเลข)

- **28 ประโยค** — เล็กมากในเชิงสถิติ ผลต่าง 0.88 vs 0.53 ใหญ่พอที่จะเชื่อได้
  แต่ผลต่างระดับ ±0.05 ไม่ควรตีความ
- **precision จาก eyeball คนเดียว** — มี bias ของผู้ประเมิน ไม่มี inter-annotator
  check
- **ไม่มี recall ที่วัดจริง** — สัญญาณ recall ที่เรามีคือจำนวน triple + จำนวน
  ประโยคว่าง เท่านั้น
- **ประเมินที่ระดับประโยค** — ยังไม่ได้ทดสอบ entity coreference / การรวม triple
  ข้ามประโยคซึ่งเป็นขั้นถัดไปของ pipeline จริง

ข้อจำกัดเหล่านี้ไม่เปลี่ยนข้อสรุป (ช่องว่างระหว่างอันดับ 1 กับ 2 กว้างเกินกว่า
noise จะอธิบายได้) แต่ควรระวังเวลาอ้างตัวเลขต่อภายนอก
